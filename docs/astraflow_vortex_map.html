AstraFlow x Vortex 接入地图

AstraFlow 是 RL 系统编排层，负责把 rollout 生成、训练、数据缓存、权重同步拆成独立服务。 Vortex 是推理加速层，第一接入面应优先放在 RaaS 启动 SGLang 的链路上。

Dataflow RaaS Trainer WeightManager Vortex
一句话

不要先改 Trainer 或 Dataflow。先把 Vortex 接到 RaaS -> SGLang launch -> entrypoint patch 这条路径。

1. AstraFlow 四组件

Central Orchestrator

Dataflow

数据中控台。负责调 RaaS 生成 rollout，收结果，过滤和缓存样本，再给 Trainer 发 batch。

  • 管理 RaaS pool
  • rollout buffer
  • staleness 过滤
  • 通知 RaaS 更新权重
Inference Service

RaaS

推理服务。启动 SGLang/vLLM，接收 prompt，执行 workflow 和 reward，返回 rollout。

  • 启动 SGLang server
  • 执行 agent workflow
  • pause / load / resume
  • 对接权重接收
Training Engine

Trainer

训练工人。向 Dataflow 拉 batch，跑 PPO/GRPO/M2PO，产生新版本权重。

  • FSDP / Megatron
  • RL update
  • notify_version
  • sender agent
Transport Layer

WeightManager

权重快递。把 Trainer 新权重放到共享内存，让 RaaS 通过 TCP pull 后加载。

  • /dev/shm double buffer
  • full / delta transfer
  • TCP receiver
  • safetensors load

Dataflow 内部代码架构

Dataflow 是数据中控：从 dataset 拿 prompt，调 RaaS pool 生成 rollout，放入 buffer， 再通过 GET /batch 给 Trainer。

Dataflow 运行时架构

Dataflow 代码阅读入口

Trainer 内部代码架构

Trainer 是训练侧：从 Dataflow 拉 batch，执行 PPO/GRPO/M2PO 更新，offload 新权重， 再调用 notify_version 进入权重同步链。

Trainer 运行时架构

Trainer 代码阅读入口

接 Vortex 时 Trainer 通常不是第一修改点。只有当 Vortex 改变 batch 字段、loss 需要的 logprob，或者权重格式时， 才需要深入 train_worker/。
读这个函数只抓三件事：先建训练模型，再连 Dataflow，最后建 WeightManager 并告诉 Dataflow trainer 已 ready。
这里是 Trainer 配置定义层。它和 RaaS 的 raas/api/cli_args.py 不是同一个文件。
这里不是训练算法本身，主要是"拉数据 + 分发数据"。如果 batch 字段不兼容，优先查这里。
这是 Trainer 最重要的函数。Vortex 接入通常不会改这里，除非 Vortex 改变 rollout batch 字段或训练 loss 所需字段。

这个文件像"训练底座构造器"，不是主循环。读它是为了知道 actor/critic/ref 和并行后端从哪来。
这里才是 RL 算法和训练后端的重区。只为 Vortex 接线时通常不用深挖。
读源码时不要找“GRPO 文件”或“M2PO 文件”。当前实现更像一条统一训练管线： compute_advantages*() 准备训练信号，ppo_update() 调训练后端， grpo_loss_fn() 根据配置切换 loss 行为。
这是 Trainer 和 RaaS 真正发生联系的权重路径。Vortex 接入不改这条，除非 Vortex 需要特殊权重格式。

WeightManager 内部代码架构

WeightManager 是权重同步链：Trainer 把新权重 offload 出来，RaaS 收到版本通知后主动 pull， 然后让 SGLang 热加载新权重。

WeightManager 运行时架构

WeightManager 代码阅读入口

点击上面总图里的模块，下面会展开对应函数链。WeightManager 要按两条线读：Trainer 先把权重放进共享内存；RaaS 收到版本通知后再主动拉取并热加载。
第三层只展开关键函数。点上面文件层图里的函数框，下面会显示函数内部顺序；小 getter、端口查找、logging helper 不单独画。
最重要的一句话：delta 不是替代 full，而是建立在本地已有 full 权重上的优化。 只要 sender 不支持、delta 未准备好、版本基准不匹配、应用失败，就回退 full。
读法：sender 不是直接“把权重塞进 SGLang”，它只是把指定版本的权重通过 TCP 发给 RaaS。 delta 是快路径，full 是兜底路径。
这张图要和 sender 图一起看：RaaS 负责“选模式、发请求、保存结果”，sender 负责“实际把 full/delta 通过 TCP 发出来”。
读法：full 传输慢一些，但语义最简单。它把一整份权重落盘，既能直接给 SGLang 加载，也能成为后续 delta patch 的本地基准。
关键点：delta 传输省的是网络传输量；RaaS 本地最终还是会落成一个完整 safetensors，这样 SGLang 的热加载逻辑不用理解 delta。
这块和 Vortex 关系不大：Vortex 主要改变 SGLang 推理实现，不改变权重同步协议。 除非 Vortex 需要不同权重格式，否则 WeightManager 通常不用动。

两个职责的边界：协议翻译只管"格式转换"，不发 HTTP 请求；发请求是 RemoteInfEngine 的事。进程启动只管"把参数变成子进程"，不管子进程启动后的通信。
为什么协议翻译单独成一个职责：SGLang 的 HTTP API 格式和 AstraFlow 内部 ModelRequest 格式不同。这层翻译让 RemoteInfEngine 完全不感知 SGLang，换成 vLLM 只需替换 Backend 实现。
怎么读： RemoteInfEngine 是统一客户端，不直接感知后端差异；差异全部由注入的 backend 对象（SGLangBackend 或 VLLMBackend）封装。 点击下方四个职责模块可展开函数级流程图。
initialize() 地址发现：优先用显式传入的 addr，其次用同进程里 launch_server 记录的本地子进程地址，再退化到 ASTRAFLOW_LLM_SERVER_ADDRS 环境变量或 name_resolve 服务发现。没有任何地址时直接抛异常。
注意：agenerate() 内部维护 _inflight_per_server 计数器（请求前 +1，完成后 -1）。这个计数供 get_generation_stats() 暴露给 manager 用于负载判断。_paused=True 时 agenerate 会等待，直到 continue_generation() 恢复。
pause_generation 的语义：发送 pause 请求后还要 sleep pause_grace_period 秒，等 in-flight 请求自然排干。Full weight 路径的 /update_weights_from_disk 自带 abort_all_requests: True；LoRA 路径则依赖上游 pause 来保证没有新请求在 load 期间进来。
为什么需要三种： check_health 只检查 HTTP 前门；SGLang 有一类特定故障是 scheduler/detokenizer 子进程被自己的 watchdog 杀掉，但 HTTP 前端还活着 —— 这时只有 check_subprocesses_alive 能检出。aget_metrics 走 Prometheus，目的是获取队列深度来做软负载均衡，不是判断存活。
当前事实： entrypoint.py 先设置 FlashInfer 兼容 env，再执行 AstraFlow 的 apply_patches()， 最后才 import SGLang 的 prepare_server_args() 和 run_server()。 Vortex 接入点： 已在这个窗口里、SGLang import 前加入 import vortex_torch，让 Vortex 的 --vortex-config / VortexConfig adapter 生效。

这个函数是“调度入口”：建 receiver、选模式、调用 full/delta，最后返回 shm_path 给 _do_weight_update()。
把它理解成“开收货站”：先知道货物规格，再准备仓库和电话线，最后告诉 sender 以后发到这里。
full 是最稳的路径：第一次同步一定要 full，因为本地还没有旧权重，delta 没有基准可打。
delta 失败会退回 full；代码里会删掉可能坏掉的 safetensors，下一轮重新全量同步。
